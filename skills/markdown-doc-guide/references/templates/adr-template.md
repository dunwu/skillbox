# 架构决策记录模板（ADR）

> **适用范围**：记录重要的架构决策、技术选型、方案取舍。每个决策一份文档。
>
> **命名规则**：`ADR-{序号}-{简短标题}.md`，如 `ADR-001-use-kafka-for-order-async.md`。
> **状态流转**：提议 → 已接受 → 已替代 / 已废弃。

> 当前状态：提议 / 已接受 / 已废弃 / 已替代

> YYYY-MM-DD

## 上下文

**章节内容意图**：描述促使此决策的业务背景、技术约束和待解决的问题。

**规范化写作指南**：

- 用事实和数据描述当前状况。
- 列出影响决策的约束条件：技术栈、团队能力、时间、成本。
- 明确需要决策的问题。

**模板示例**：

订单系统在促销高峰期面临写入瓶颈。当前同步写入 MySQL 的方式，P99 延迟达 3 秒。需要引入异步化方案削峰填谷。约束条件：

- 团队具备 Kafka 和 RocketMQ 运维能力。
- 消息可靠性要求：订单消息不允许丢失。
- 延迟要求：订单从创建到落库不超过 5 秒。

## 决策

**章节内容意图**：清晰陈述做出的决策及核心理由。

**规范化写作指南**：

- 用一句话明确陈述决策结果。
- 列出 2-5 条核心理由。
- 理由应引用具体的约束条件或评估数据。

**模板示例**：

我们选择 Kafka 作为订单异步化的消息队列，而非 RocketMQ 或 Redis Stream。

理由：

1. **吞吐量**：压测数据显示 Kafka 在同等硬件下吞吐量是 RocketMQ 的 1.5 倍（80,000 vs 53,000 msg/s）。
2. **团队经验**：运维团队已有 3 年 Kafka 集群运维经验，无 RocketMQ 生产运维经验。
3. **生态兼容**：Kafka 已与现有 Flink 实时计算链路集成，无需额外适配。
4. **成本**：Kafka 集群已就绪，无需新增基础设施预算。

## 备选方案

**章节内容意图**：记录被排除的方案及其排除理由，防止后续重复讨论。

**规范化写作指南**：

- 列出所有被认真评估的备选方案。
- 对每个方案说明优缺点及最终排除理由。
- 用表格对比核心维度。

**模板示例**：

| 维度 | Kafka | RocketMQ | Redis Stream |
|:-----|:------|:---------|:-------------|
| 吞吐量 | 80,000 msg/s | 53,000 msg/s | 100,000+ msg/s |
| 消息可靠性 | 高（ISR 副本） | 高（同步刷盘） | 低（内存优先） |
| 团队经验 | 3 年 | 0 年 | 1 年（非生产） |
| 运维成本 | 已有集群 | 需新部署 | 已有集群但用途不同 |
| 延迟 | ~10 ms | ~5 ms | ~1 ms |

排除理由：

- **RocketMQ**：团队无生产运维经验，引入风险高；吞吐量不占优。
- **Redis Stream**：消息可靠性不满足订单场景要求（内存优先，宕机可能丢消息）。

## 后果

**章节内容意图**：描述此决策带来的正面和负面影响。

**规范化写作指南**：

- **正面后果**：决策带来的直接收益。
- **负面后果**：决策带来的风险、限制或额外成本。
- **需跟进事项**：决策后需要补充的工作。

**模板示例**：

**正面后果**：

- 订单写入 P99 延迟预计从 3 秒降至 50ms 以内。
- 系统可支撑 5,000 QPS 峰值流量。

**负面后果**：

- 引入 Kafka 导致系统复杂度增加，需处理消费者积压、重复消费等问题。
- 订单创建从同步变为异步，客户端需轮询或 WebSocket 获取最终结果。
- 运维需增加 Kafka 监控和告警。

**需跟进事项**：

- 补充 Kafka 消费者幂等方案设计。
- 制定 Kafka 集群容量规划和扩容预案。
- 设计客户端轮询/推送方案。

## 使用提示

- 每份 ADR 只记录一个决策，避免把多个决策混为一谈。
- 状态变更时同步更新本文档，已替代的旧 ADR 应链接到替代它的新 ADR。
- 关联决策表格帮助读者追溯决策之间的依赖关系。
