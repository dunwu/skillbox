# SDD 开发工作流规范

> **摘要**
>
> - **核心约束**：AI 是参谋不是决策者；spec.md 需含验收标准+非功能需求+开放问题（全部解决才算完成）；plan.md 需 ≥2 方案对比+ADR；tasks.md 单 task ≤半天且必须含验收条件
> - **关键阈值**：单 task 预计 ≤4h、方案对比 ≥2 个、spec 验收标准每条可独立测试
> - **常见违规**：跨阶段跳跃、spec.md 缺非功能需求、plan.md 只列一个方案、tasks.md 无验收条件

> **版本**：v1.0 | 最后更新：2026-06-09 | 适用 SKILL 版本：≥ v1.0.0

本文档为 SKILL.md §1 SDD 工作流各阶段的详细规范。

---

## 1. 需求分析

### 1.1. AI 角色定位

AI 是**参谋，不是决策者**。职责：枚举边界条件、澄清模糊需求、识别技术风险；所有方向性判断必须由人确认。

### 1.2. 触发方式

```
加载 brainstorming Skill，向 AI 描述需求背景与初步想法。
```

### 1.3. AI MUST 主动澄清的问题

产出 `spec.md` 前，AI 必须确认以下维度，缺失则主动提问：

| 维度       | 澄清要点                            |
| ---------- | ----------------------------------- |
| 功能边界   | 哪些功能在本次范围内，哪些明确排除  |
| 用户与场景 | 谁在什么场景下使用，核心诉求是什么  |
| 异常与边界 | 入参为空 / 超限 / 并发时的预期行为  |
| 非功能需求 | 性能目标、数据量级、兼容性要求、SLA |
| 验收标准   | 如何判断"做完了"且"做对了"          |
| 开放问题   | 当前无法确认、需要决策的事项        |

### 1.4. spec.md 模板

```markdown
## 背景与目标

<!-- 一句话说明为什么要做，解决什么问题 -->

## 用户故事

<!-- As a [用户]，I want [功能]，So that [价值] -->

## 功能范围

### In Scope

### Out of Scope

## 验收标准

<!-- 每条标准必须可测试，推荐 Given-When-Then 格式 -->

- [ ] Given ... When ... Then ...

## 非功能需求

- 性能：
- 安全：
- 兼容性：

## 开放问题

<!-- 尚未确认、需要决策的事项，确认后删除对应条目 -->
```

### 1.5. 阶段约束

- **MUST NOT** 在 `spec.md` 经用户确认前，输出任何技术方案或代码
- **MUST NOT** 跳过非功能需求（性能、安全是常见遗漏）
- **MUST** 开放问题全部解决后才标记需求分析完成（"解决"定义：用户在对话中明确回复决策，或 AI 已收到明确需求说明使该问题不再成立；**MUST NOT** 由 AI 自行标记开放问题为已解决）
- **MUST** 在写 `spec.md` 前读取 `GLOSSARY.md` 和 `ARCHITECTURE.md`
- **MUST NOT** 未读上述文档直接输出 `spec.md`

## 2. 概要设计（HLD）

### 2.1. 目标

明确模块划分与接口契约，为 tasks.md 拆解提供依据。

### 2.2. plan.md 必须包含

| 章节       | 内容要求                                    |
| ---------- | ------------------------------------------- |
| 方案对比   | ≥ 2 个可行方案，列出各自优缺点与适用条件    |
| 架构决策   | 选定方案及理由，记录被否决方案的原因（ADR） |
| 模块划分   | 涉及的模块 / 服务，职责边界说明             |
| 接口契约   | 关键接口的方法签名、入参、出参、错误码      |
| 数据模型   | 核心表结构 / 文档结构 / 缓存 Key 设计       |
| 风险与依赖 | 外部依赖、技术风险、降级策略                |

### 2.3. plan.md Markdown 模板

```markdown
## 一、方案对比

| 方案   | 优点 | 缺点 | 适用条件 |
| ------ | ---- | ---- | -------- |
| 方案 A | ...  | ...  | ...      |
| 方案 B | ...  | ...  | ...      |

## 二、架构决策（ADR）

**选定方案**：方案 X

**理由**：...

**被否决方案**：方案 Y — 原因：...

## 三、模块划分

| 模块 | 职责 | 影响范围 |
| ---- | ---- | -------- |
| ...  | ...  | ...      |

## 四、接口契约

### `{ServiceName}.{methodName}()`

| 参数 | 类型 | 说明 |
| ---- | ---- | ---- |
| ...  | ...  | ...  |

**返回值**：`{ResponseWrapper}<XxxVO>`

**错误码**：`{ResultCode}.XXX`

## 五、数据模型

<!-- 核心表结构 / 缓存 Key / 文档结构 -->

## 六、风险与依赖

| 风险 | 影响 | 降级策略 |
| ---- | ---- | -------- |
| ...  | ...  | ...      |
```

### 2.4. 技术选型评估维度

做技术选型时，AI 必须从以下维度给出分析，不得仅凭惯性选择：

1. **复用优先**：现有组件是否已满足需求
2. **团队熟悉度**：引入新技术的学习与维护成本
3. **性能与容量**：数据量级、QPS 是否匹配
4. **运维成本**：监控、告警、故障排查的复杂度
5. **长期演进**：技术选型是否锁定、未来扩展性

### 2.5. 阶段约束

- **MUST NOT** 在方案对比中只列一个方案
- **MUST NOT** 在接口契约未定义前进入详细设计
- **MUST** 等待架构评审通过后才进入下一阶段
- **MUST** 在输出 `plan.md` 前读取 `ARCHITECTURE.md` 和 `API-CONTRACTS.md`
- **SHOULD** 在涉及可配置逻辑时读取 `CONFIGURATION.md`
- **MUST** 在详细设计时按需加载对应 Skill refs（如 `java-guide.md`、`api-guide.md` 等）

## 3. 详细设计（LLD）

### 3.1. 目标

将 `plan.md` 拆解为 AI 可逐条执行的原子任务，每条任务独立、可验证。

### 3.2. tasks.md 规范

**任务粒度**：每个 task 预计工时 ≤ 半天（4h），可独立实现与测试。

**每个 task 必须包含：**

```markdown
### Task N：{动词 + 名词，描述做什么}

**目标**：一句话说明本 task 的交付物
**优先级**：P0（核心链路）/ P1（重要）/ P2（增强）
**前置条件**：依赖哪些 task 完成（并行 / 串行）
**实现步骤**：

1. ...
2. ...
   **验收条件**：

- [ ] ...
- [ ] ...
```

**任务关系标注**：

```markdown
<!-- 串行（必须按序）-->

Task 1 → Task 2 → Task 3

<!-- 并行（可同时进行）-->

Task 1 ┬→ Task 2
└→ Task 3
→ Task 4（合并后）
```

### 3.3. 阶段约束

- **MUST NOT** 存在无验收条件的 task
- **MUST NOT** 任务粒度过大（单 task 超过半天需强制拆分）
- **MUST** 等待用户确认 `tasks.md` 后才开始编码
- **MUST** 拆解 task 前读取对应模块的 `docs/{module}.md`，理解职责边界
- **MUST** 涉及公共 API 的 task 必须对照 `API-CONTRACTS.md` 拆解

## 4. 端到端示例

### 4.1. 场景：文章发布功能

#### 4.1.1. spec.md（需求分析产出）

```markdown
## 背景与目标

作者需要发布文章，发布后文章对外可见，同时需要通知关注者。

## 用户故事

As a 内容作者，I want 发布文章后文章立即对外可见，So that 读者可以搜索和阅读。

## 验收标准

- [ ] Given 作者已登录且文章内容不为空 When 点击发布 Then 文章状态变为"已发布"、发布时间被记录
- [ ] Given 文章内容为空 When 点击发布 Then 返回 PARAM_INVALID 错误
- [ ] Given 作者不存在 When 点击发布 Then 返回 AUTHOR_NOT_FOUND 错误

## 非功能需求

- 性能：发布接口 P99 < 200ms
- 安全：仅文章作者本人可发布

## 开放问题

（已全部解决）
```

#### 4.1.2. plan.md（概要设计产出，节选）

```markdown
## 一、方案对比

| 方案 | 优点 | 缺点 |
| 同步发布 | 简单直接 | 发布耗时影响响应 |
| 异步发布+回调 | 响应快 | 实现复杂度高 |

## 二、架构决策

**选定方案**：同步发布（首版 MVP，数据量可控）
**理由**：当前 QPS < 100，同步方案足够

## 四、接口契约

### `ArticleApplicationService.publish(Long articleId)`

| 参数 | 类型 | 说明 |
| articleId | Long | 文章 ID |
**返回值**：`{ResponseWrapper}<ArticleVO>`
**错误码**：`ARTICLE_NOT_FOUND` / `PARAM_INVALID`
```

#### 4.1.3. tasks.md（详细设计产出）

```markdown
### Task 1：创建 Article 实体与 Repository

**目标**：ArticleDO、ArticleRepository 接口与实现
**优先级**：P0
**前置条件**：无
**验收条件**：

- [ ] ArticleDO 包含 id/title/content/authorId/status/publishTime 字段
- [ ] ArticleRepository 接口定义 findById / save 方法
- [ ] ArticleRepositoryImpl 使用 ArticleDao 实现

### Task 2：实现发布业务逻辑

**目标**：ArticleApplicationService.publish() 方法
**优先级**：P0
**前置条件**：Task 1 完成
**验收条件**：

- [ ] 作者不存在时抛 ARTICLE_NOT_FOUND
- [ ] 内容为空时抛 PARAM_INVALID
- [ ] 发布后 status=2、publishTime 非空
- [ ] 返回 {ResponseWrapper}<ArticleVO>

### Task 3：编写发布单元测试

**目标**：ArticleApplicationServiceTest 覆盖正常/异常分支
**优先级**：P0
**前置条件**：Task 2 完成
**验收条件**：

- [ ] 测试作者不存在场景
- [ ] 测试内容为空场景
- [ ] 测试正常发布场景
- [ ] 全部通过
```

### 5.1. 引用约束速查表

| SDD 阶段 | 必读文档                                | 按需加载 Skill                       | 禁止行为                 |
| -------- | --------------------------------------- | ------------------------------------ | ------------------------ |
| 需求分析 | `GLOSSARY.md` + `ARCHITECTURE.md`       | `brainstorming`                      | 未读文档直接写 `spec.md` |
