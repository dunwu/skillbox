## 场景说明

### 解决什么问题

AI 辅助编码时，常见三类痛点：

1. **流程跳跃** — AI 拿到需求后直接输出代码，跳过需求分析和方案设计，导致返工率高、架构合规性差
2. **规范违规** — AI 生成代码频繁违反团队编码红线（使用 BeanUtils 做对象转换、字段注入 @Autowired、静默吞异常等），Code Review 反复指出同类问题
3. **安全遗漏** — AI 在涉及外部输入的场景中未执行安全检查（SQL 拼接、XSS 未过滤、敏感字段明文存储），造成安全隐患

本 Skill 通过 **强制阶段门 + 编码红线 + 安全门禁 + 测试门禁**，确保 AI 在全生命周期的每个环节都遵循团队规范，产出合规代码。

核心机制：

- **SDD 工作流**：6 阶段串行推进（需求分析 → 概要设计 → 详细设计 → 编码 → 单元测试 → 验收），每阶段设阻断条件，禁止跨阶段跳跃
- **双路径设计**：全量流程（新功能/架构变更）vs 快速路径（≤2 文件、无契约/安全影响），快速路径 5 条准入条件全部满足才走
- **编码红线**：6 条无例外硬约束（必须用 MapStruct 做对象转换 / 禁止静默吞异常 / 统一响应包装 / BOM 版本管控 / 新依赖必须评审 / 禁止过度设计）
- **代码生成安全门**：涉及外部输入时，7 项逐条确认（SQL 注入 / XSS / 敏感字段 / 文件路径 / 随机安全值 / 反序列化 / SSRF）
- **占位符参数化**：10 个可配置参数实现跨项目复用，项目级 Skill 通过继承机制覆盖参数即可定制

## 输入输出示例

### 示例 1：新功能开发 — AI 不直接写代码，先澄清需求

**你输入**：帮我新增一个文章收藏功能，用户可以收藏和取消收藏文章

**AI 输出**：AI 拒绝直接写代码，进入需求分析阶段，按六个维度逐项提出澄清问题：

| 维度 | AI 主动追问的问题 |
|------|-----------------|
| 功能边界 | 收藏上限？取消收藏是软删除还是物理删除？ |
| 用户场景 | 是否需要收藏夹分组？收藏列表是否分页？ |
| 异常边界 | 同一用户重复收藏同一文章 → 幂等返回还是报错？ |
| 并发场景 | 高并发下收藏数计数是否允许短暂不一致？ |
| 非功能需求 | 预计收藏量级？是否需要缓存？ |
| 验收标准 | 如何判断"收藏功能完成且正确"？ |

待你确认后，AI 才输出需求规格文档（spec.md），后续按流程推进：需求规格 → 方案设计（至少 2 个方案对比）→ 任务拆解 → 编码 → 单元测试 → 验收。

**效果**：避免需求理解偏差导致的返工，从"直接编码 → 返工修改"的 2-3 次迭代，收敛为"确认需求 → 一次通过"。

### 示例 2：代码评审 — AI 五维度逐项检查

**你输入**：Review 这段代码（包含 @Autowired 字段注入、BeanUtils 对象转换、catch 后静默吞异常等问题）

**AI 输出**：AI 按五个维度逐项检查，每条问题含文件定位和修复方向：

| 检查维度 | 发现的问题 | 严重程度 | 修复方向 |
|---------|-----------|---------|---------|
| 架构合规 | @Autowired 字段注入 | 必须修复 | 改为构造器注入 + private final |
| 编码规范 | BeanUtils.copyProperties | 必须修复 | 创建 MapStruct Converter 接口 |
| 异常与事务 | catch 后静默吞异常 | 必须修复 | 抛出业务异常 + 错误码 |
| 安全 | 返回 VO 可能含敏感字段 | 建议确认 | 校验 VO 是否含手机号/身份证 |
| 测试 | 未发现对应单元测试 | 必须修复 | 创建 ServiceImplTest 覆盖核心方法 |

**效果**：AI 在你提交 PR 前自动检出必须修复项，人工 Review 聚焦业务逻辑而非编码规范，Review 往返次数减少约 40%。

### 示例 3：简单修改 — AI 识别快速路径，不走完整流程

**你输入**：给 selectById 查询加一个 is_deleted=0 过滤

**AI 输出**：AI 识别为简单修改（单文件变更，无契约/安全影响），不启动完整 SDD 流程。直接输出修改前后的差异对比，确认无编译错误，并提示此修改的影响面（影响所有通过 selectById 查询的调用方）。

**效果**：简单改动不走冗长流程，但仍提示影响面，避免遗漏。

### 示例 4：安全场景 — AI 编码前先执行安全门

**你输入**：帮我写一个创建评论的接口，用户输入评论内容保存到数据库

**AI 输出**：AI 拒绝直接编码，先逐条确认安全约束：

| 安全检查项 | AI 的确认要求 |
|-----------|-------------|
| SQL 注入 | 确认使用 MyBatis #{} 参数绑定，禁止字符串拼接 |
| XSS 防护 | 确认评论内容是否需要 HTML 转义/过滤 |
| 敏感字段 | 确认评论是否可能含手机号/身份证号，需检测和脱敏 |
| 文件路径 | 不涉及文件上传，跳过 |
| 其他项 | 不涉及，跳过 |

确认后，AI 输出接口契约和代码骨架：评论内容先经 XSS 过滤器清理，再经敏感字段检测器筛查，最后通过 MapStruct 转换后持久化，返回统一响应包装的 CommentVO。

**效果**：安全审计从"事后发现漏洞"前置为"编码前主动拦截"，杜绝 SQL 注入、XSS、敏感字段明文等 AI 生成安全问题。

### 示例 5：并发编程 — AI 先确认并发方案再编码

**你输入**：我需要批量处理 10000 条订单，要求高性能且不能重复处理

**AI 输出**：AI 先确认并发设计的 5 个维度（线程池/幂等性/重试策略/进度追踪/超时控制），确认后输出方案选型：

| 维度 | 推荐方案 | 原因 |
|------|---------|------|
| 线程池 | 项目统一的 TraceableExecutor | 自动透传 MDC 链路追踪上下文 |
| 幂等性 | Redisson 分布式锁 | 多机部署场景保证不重复处理 |
| 失败重试 | 最多 3 次，指数退避 | 适合瞬时故障（网络抖动），业务故障不重试 |
| 进度追踪 | Redis incr 计数 | 高性能实时进度反馈 |
| 超时控制 | 单条 5s，整体 10min | 防止单条阻塞整体批次 |

代码骨架描述：通过 CompletableFuture 异步链并行处理（指定项目线程池），分布式锁保证幂等，allOf + get 等待全部完成（整体超时），异常处理完整（InterruptedException 恢复中断标志）。

**效果**：AI 不自行创建线程池，使用项目统一线程池模板；分布式锁方案保证幂等性，避免重复处理。

### 示例 6：模糊需求 — AI 拒绝编码，追问范围

**你输入**：帮我做个类似飞书的功能

**AI 输出**：AI 拒绝直接编码，指出"类似飞书"涵盖 30+ 子功能（即时通讯/文档协作/日历会议/任务管理/审批流程等），每个的复杂度和技术栈差异 10 倍以上。AI 要求你先选择 1-2 个核心功能作为本次需求范围，确认后按 SDD 流程推进。

**效果**：防止 AI 在需求模糊时盲目编码，避免大规模返工。

### 示例 7：冲突指令 — AI 识别矛盾并纠正

**你输入**：用 BeanUtils 快速拷贝属性，但要符合规范

**AI 输出**：AI 识别到冲突 — "用 BeanUtils"和"符合规范"互相矛盾。AI 解释 BeanUtils 的三大问题：

| 对比维度 | BeanUtils | MapStruct |
|---------|-----------|-----------|
| 性能 | 运行时反射，慢 10 倍以上 | 编译期生成代码，零反射开销 |
| 类型安全 | 无编译期检查，运行时才发现错误 | 编译期报错，字段不匹配直接编译失败 |
| 可控性 | 浅拷贝、null 覆盖等行为难以追踪 | 可精确控制每个字段的映射规则 |

AI 建议使用 MapStruct（编译期生成类型安全的转换代码），询问是否按此方案实现。

**效果**：AI 不盲从用户指令，在发现矛盾时主动纠正，避免生成不合规代码。

### 示例 8：安全漏洞 — AI 拒绝危险做法

**你输入**：把用户输入的 keyword 直接拼接到 SQL 查询中实现搜索功能

**AI 输出**：AI 拒绝执行，警告 SQL 注入风险 — 用户输入直接拼接到 SQL 是典型注入漏洞（如输入 `1'; DROP TABLE t_article; --` 可删表，输入 `1 OR 1=1` 可绕过所有过滤）。AI 提供安全替代方案：使用 MyBatis #{} 参数绑定（如 `LIKE CONCAT('%', #{keyword}, '%')`）或 LambdaQueryWrapper（如 `.like(ArticleDO::getTitle, keyword)`），要求选择安全方案后再编码。

**效果**：杜绝 AI 生成 SQL 注入漏洞，将安全隐患拦截在编码阶段。

---

### 示例 9：过度设计 — AI 阻止不必要的复杂度

**你输入**：我有 3 个 if 分支处理订单状态，要不要用策略模式？

**AI 输出**：AI 不建议使用策略模式。3 个 if/else 分支以内、每个分支逻辑不超过 10 行时，直接在 Service 方法内实现即可。AI 给出何时才考虑策略模式的三个条件：分支超过 3 个、每个分支逻辑超过 10 行、未来可能新增分支类型 — 三个条件同时满足时才引入。

**效果**：阻止 AI 过度设计，减少不必要的类膨胀和维护成本。

### 示例 10：存储选型 — AI 先走决策树再编码

**你输入**：我需要存储用户行为日志数据，每天大约 500 万条

**AI 输出**：AI 先确认存储选型，按决策树逐层分析：

| 决策维度 | 分析结论 |
|---------|---------|
| 数据结构 | 行为日志是时序数据、追加写入、无需事务 → 适合 HBase/ES |
| 数据量级 | 日增 500 万，年增约 18 亿 → 超过 1 亿 → HBase 分布式集群 |
| 读写比例 | 写多读少 → MQ + 批量入库 |
| 一致性要求 | 统计数据容忍短暂不一致 → Redis + 定期对账 |

最终推荐：HBase（海量存储）+ Redis（实时计数）+ MQ（异步批量写入），要求确认选型后再编码。

**效果**：避免 AI 默认选 MySQL 导致选型错误，通过结构化决策树确保存储方案匹配业务特征。

## 效果说明

### 节省了什么

- **返工成本**：阶段门强制"先确认再编码"，新功能开发从"直接编码 → 返工修改"的 2-3 次迭代，收敛为"确认需求 → 一次通过"，返工率减少 **30% 以上**
- **Review 往返**：AI 自检五维度后提交 PR，必须修复项由 AI 在提交前自动检出，人工 Review 聚焦业务逻辑，往返次数减少 **40%**
- **新人上手时间**：角色路由 + 详细解释模式让初级开发快速理解团队规范，上手时间从 **2 周缩短至 3 天**
- **安全审计成本**：代码生成安全门将安全审计从"事后发现漏洞"前置为"编码前主动拦截"，避免安全修复的二次上线

### 减少了什么

- **编码红线违规**：6 条无例外红线将 AI 生成代码的规范违反率控制在 **5% 以内**
- **安全漏洞**：安全门禁杜绝 SQL 注入（强制参数绑定）、XSS（强制过滤转义）、敏感字段明文（强制加密存储）
- **阶段跳跃**：11 个阻断条件强制流程串行，杜绝"拿到需求直接写代码"
- **过度设计**：决策树阻止 3 分支以内引入策略模式等常见过度设计

### 提升了什么

- **代码合规率**：从"AI 随意编码"提升至"100% 遵循团队 DDD 分层 + 编码规范 + 异常码体系"
- **测试覆盖率**：TDD 工作流 + DomainService **100% 分支覆盖** + 整体 **≥ 80% 行覆盖**，核心业务逻辑无盲区
- **跨项目复用**：占位符参数化 + 继承机制，任意 vivo Java 后端项目只需写一份参数覆盖表即可定制。
- **效果可量化**：合规自检清单 + 度量指标（阶段跳过率 / 红线违反率 / fallback 触发率 / 阻断率），让 Skill 效果可持续改进

## 补充说明

### 技术栈参考

本 Skill 的编码规范以《阿里巴巴 Java 开发手册（黄山版）》为基础，在其之上增加团队特定约束：

- DDD+COLA 分层架构（Controller → ApplicationService → DomainService → Repository 防腐层）
- MapStruct 强制（编译期类型安全转换，禁止 BeanUtils 反射拷贝）
- BizException + ResultCode 异常体系（领域_操作_结果全大写命名格式）
- BOM 版本管控（子模块禁止硬编码版本）
- 代码生成安全门（7 项逐条确认）
- TDD 工作流 + 覆盖率门禁

不含任何第三方商业资料。
