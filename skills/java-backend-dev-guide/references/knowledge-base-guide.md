# 渐进式本地知识库构建规范

> **定位**：指导 AI Agent 在 SDD 全生命周期中按需引用知识库，确保知识准确、及时、不膨胀。
>
> **核心约束**：L2 层文档总量必须 < 50K tokens；超过时拆分模块文档，禁止全量加载。
>
> v1.0 | 2026-06-09

---

## 1 分层架构设计

### 1.1 三层模型

```text
Layer 1: Rule/Skill          - 行为约束层   ← 会话级自动加载
Layer 2: docs/ + specs/      - 领域知识层   ← 任务级按需索引
Layer 3: 代码注释             - 内联知识层   ← 编码时实时读取
              ▲ 渐进外露：越底层加载频率越高
```

| 层级      | 产出物                             | 内容                                | 加载时机         | 维护主体   | 更新频率     |
| --------- | ---------------------------------- | ----------------------------------- | ---------------- | ---------- | ------------ |
| L1 Rule   | `AGENTS.md`                        | 不可降级行为护栏、安全底线          | 每次会话自动加载 | 技术负责人 | 季度         |
| L1 Skill  | `SKILL.md` + `refs/`               | 场景化编码规约、流程模板            | 按场景触发加载   | 技术负责人 | 月度         |
| L2 docs/  | 模块文档 / 架构文档 / 术语表       | 模块职责、API契约、配置项、架构决策 | 编码前按需索引   | 模块Owner  | 漂移检测驱动 |
| L2 specs/ | `spec.md` / `plan.md` / `tasks.md` | 需求规格、设计方案、任务清单        | 随 SDD 阶段产出  | 需求Owner  | 需求生命周期 |
| L3 注释   | JavaDoc / 行内注释                 | 设计意图、非 obvious 决策           | 编码时实时读取   | 开发者     | 编码时同步   |

### 1.2 加载策略

| 场景                | 加载层级 | 具体操作                                       |
| ------------------- | -------- | ---------------------------------------------- |
| 新会话启动          | L1       | 自动加载 `AGENTS.md`                           |
| 任务场景匹配        | L1       | 按需触发对应 `SKILL.md` 及 refs                |
| 接触新模块代码      | L1 + L2  | 先读取 `docs/` 下最相关的 1-2 篇文档，再读代码 |
| 编码中遇到设计问题  | L2 + L3  | 查阅模块文档 + 相关类 JavaDoc                  |
| 需求分析 / 设计阶段 | L2       | 读取 `ARCHITECTURE.md` + 相关模块文档          |
| 测试阶段            | L1 + L2  | 加载 `test-guide.md` + 查阅 API 契约文档       |

**约束**：L2 层文档总量必须 < 50K tokens。超过时拆分模块文档，禁止全量加载。

## 2 本地知识库最小集

### 2.1 项目级最小集（任何项目启动时必须存在）

| 文件               | 内容                                   | 验收标准                | 缺失时后果                                  |
| ------------------ | -------------------------------------- | ----------------------- | ------------------------------------------- |
| `README.md`        | 项目定位、模块划分、技术栈、启动命令   | 新人 5 分钟理解项目边界 | Agent 无法判断模块职责                      |
| `ARCHITECTURE.md`  | 分层架构、核心类关系、数据流、关键决策 | AI 据此生成合规代码     | Agent 猜测架构，导致分层混乱                |
| `GLOSSARY.md`      | 业务术语、技术术语、缩写对照           | 消除命名歧义            | Agent 使用不一致的命名                      |
| `API-CONTRACTS.md` | 对外暴露的 API/DTO/错误码/SPI          | AI 引用零猜测           | Agent 猜测 API 签名，导致调用错误或重复定义 |
| `CONFIGURATION.md` | 配置项、默认值、生效范围               | AI 不硬编码             | Agent 硬编码配置值，使用错误默认值          |
| `docs/{module}.md` | 单模块职责边界、公共 API、配置项       | 外部调用者无需读源码    | Agent 重复造轮子或误用 API                  |

### 2.2 模块级最小集（每个业务模块必须存在）

```text
docs/
├── README.md              # 入口：模块定位、与上下游关系
├── ARCHITECTURE.md        # 模块内部分层、核心类、数据流
├── GLOSSARY.md            # 模块特有术语
├── API-CONTRACTS.md       # 对外暴露的 API/DTO/错误码/SPI
├── CONFIGURATION.md       # 配置项、默认值、生效范围
└── {sub-module}.md        # 子系统文档（按需）
```

### 2.3 最小集优先级（资源不足时的建设顺序）

```
P0：README.md + GLOSSARY.md      → 消除最基本的歧义
P1：API-CONTRACTS.md             → 防止 API 误用和重复建设
P2：ARCHITECTURE.md              → 指导复杂设计决策
P3：CONFIGURATION.md             → 防止硬编码和配置泄漏
```

## 3 知识漂移检测

### 3.1 触发时机

| 触发事件                       | 检测范围                         | 优先级              |
| ------------------------------ | -------------------------------- | ------------------- |
| **代码变更后**（编码阶段）     | 变更涉及的 API / 配置 / 模块文档 | P0 - 每次提交前     |
| **任务完成时**（SDD 验收阶段） | `specs/` 与 `docs/` 一致性       | P0 - 每次需求交付前 |
| **CI/CD 构建时**               | 全量 `docs/` 与代码签名比对      | P1 - 每日 / 每次 MR |
| **定期巡检**（每周）           | 全仓库文档时效性、过期标记       | P2 - 每周五         |
| **Release 前**                 | `ARCHITECTURE.md` 与当前架构快照 | P1 - 每次发布前     |

### 3.2 检测方法

**方法 1：确定性规则扫描（必须实现）**

| 检查项       | 规则                                                               | 实现方式                                                                   |
| ------------ | ------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| API 签名漂移 | `API-CONTRACTS.md` 中的方法签名必须与源码一致                      | 正则提取文档中的方法签名，与 `src/` 中实际签名比对                         |
| 配置项漂移   | `CONFIGURATION.md` 中的 Key 必须在配置类或 `.yaml` 中存在          | 正则提取文档中的配置 Key，与 `@ConfigurationProperties` 字段或 yaml 键比对 |
| 模块依赖漂移 | `ARCHITECTURE.md` 中的模块关系必须与 `pom.xml` / ArchUnit 测试一致 | 解析 pom 依赖树与文档中的模块关系图比对                                    |
| 术语漂移     | `GLOSSARY.md` 中的术语必须在代码中统一使用                         | 检查代码中是否存在同一概念的多种命名                                       |

**方法 2：AI 辅助审查（辅助手段）**

仅在确定性规则通过后执行，用于发现结构性问题。

**约束**：AI 辅助审查 **MUST NOT** 替代确定性规则扫描。

### 3.3 漂移处理流程

```
触发漂移检测
  │
  ├─ 确定性规则未通过 → 阻断提交/合并 → 开发者补充文档 → 重新检测
  │
  └─ 确定性规则通过 → 允许提交 → AI 辅助审查 → 发现潜在漂移？
       │                                    ├─ 是 → 创建文档更新任务
       │                                    └─ 否 → 完成
```

## 4 SDD 各阶段知识引用约束

### 4.1 需求分析阶段

| 知识源            | 引用目的                         | 约束                           |
| ----------------- | -------------------------------- | ------------------------------ |
| `GLOSSARY.md`     | 统一业务术语，消除需求理解歧义   | **MUST** 在写 `spec.md` 前读取 |
| `ARCHITECTURE.md` | 判断需求归属模块，识别边界       | **MUST** 在模块划分前读取      |
| 历史 `specs/`     | 参考同类需求的验收标准和设计模式 | **SHOULD** 在需求拆解时检索    |

**禁止**：未读 `GLOSSARY.md` 和 `ARCHITECTURE.md` 直接输出 `spec.md`。

### 4.2 设计阶段

| 知识源             | 引用目的                     | 约束                              |
| ------------------ | ---------------------------- | --------------------------------- |
| `ARCHITECTURE.md`  | 确保设计符合现有分层和扩展点 | **MUST** 在输出 `plan.md` 前读取  |
| `API-CONTRACTS.md` | 复用现有 API，避免重复定义   | **MUST** 在接口设计前读取         |
| `CONFIGURATION.md` | 判断是否需要新增配置项       | **SHOULD** 在涉及可配置逻辑时读取 |
| Skill `refs/`      | 遵循编码规范和设计模式       | **MUST** 在详细设计时按需加载     |

### 4.3 编码阶段

| 知识源                  | 引用目的                                     | 约束                            |
| ----------------------- | -------------------------------------------- | ------------------------------- |
| 模块 `docs/{module}.md` | 理解模块职责边界，防止越界实现               | **MUST** 首次接触模块时读取     |
| `API-CONTRACTS.md`      | 确保实现与契约一致                           | **MUST** 在实现公共 API 时读取  |
| Skill `refs/`           | 遵循具体技术栈规范（MyBatis/Dubbo/Redis 等） | **MUST** 在使用对应技术时加载   |

**加载顺序**（首次接触模块时）：

```
1. 读取 docs/ 下最相关的 1-2 篇文档（不超过 2 篇）
2. 按需加载对应 Skill refs（不超过 3 个）
3. 开始编码，过程中随时查阅代码注释
4. 引用外部符号前，用工具验证存在性
```

### 4.4 测试阶段

| 知识源                | 引用目的                    | 约束                    |
| --------------------- | --------------------------- | ----------------------- |
| `spec.md`             | 验证测试覆盖所有验收标准    | **MUST** 测试设计前读取 |
| `API-CONTRACTS.md`    | 验证测试用例与 API 契约一致 | **MUST** 接口测试前读取 |
| Skill `test-guide.md` | 遵循 Mock 策略、覆盖率要求  | **MUST** 编写测试前加载 |

## 5 知识库与代码冲突处理

### 5.1 处理原则

```
代码即真相（Code is Truth）
```

- **文档与代码冲突时，以代码为准**
- **Agent 不得修改代码以迁就过期文档**
- **Agent 必须标记文档过期，并停止引用**

### 5.2 处理流程

**Step 1：停止引用并标记**

```
【知识库冲突】发现 docs/{module}.md 与实际代码不一致
- 文档描述：[文档内容]
- 实际代码：[代码片段]
- 冲突类型：[API不存在/架构变更/配置废弃/规约冲突]
处理：停止引用该文档，以代码实现为准
```

**Step 2：记录漂移项**

```markdown
## 漂移检测

- [模块名]-[文档名]：[冲突描述] → 需更新 [目标文档]
```

**Step 3：通知维护者**

| 文档层级       | 维护者     | 通知方式                 |
| -------------- | ---------- | ------------------------ |
| Rule / Skill   | 技术负责人 | 在任务评论中 @技术负责人 |
| docs/ 模块文档 | 模块 Owner | 在任务评论中 @模块Owner  |
| specs/         | 需求 Owner | 在验收阶段提出           |

**Step 4：临时恢复机制**

| 冲突严重程度              | 降级策略                                 |
| ------------------------- | ---------------------------------------- |
| 轻微（单个 API 命名差异） | 以代码为准继续编码，记录漂移             |
| 中等（模块职责边界变更）  | 查阅代码注释和同类实现推断意图，记录漂移 |
| 严重（架构分层完全变更）  | 暂停编码，请求人工确认新架构设计         |

## 6 Rule 与 Skill 治理

### 6.1 维护职责

| 角色       | 职责范围                | 指标                |
| ---------- | ----------------------- | ------------------- |
| 技术负责人 | `AGENTS.md`、通用 Skill | 季度审计通过率 100% |
| 技术负责人 | 项目级 Skill、架构文档  | 覆盖率 ≥ 80%        |
| 模块 Owner | 模块 `docs/`            | 漂移项 ≤ 48h 关闭   |
| 开发者     | 代码注释 + 漂移检测执行 | 自检全通过          |
| Reviewer   | 文档同步性验证          | 过期阻塞率 ≤ 5%     |

### 6.2 更新频率

| 类型       | 频率         | 触发条件             |
| ---------- | ------------ | -------------------- |
| Rule       | 季度         | 安全事件、架构调整   |
| 通用 Skill | 月度         | 技术栈升级、问题复盘 |
| 项目 Skill | 按需         | 新模块接入、冲突解决 |
| docs/      | 漂移检测驱动 | 代码变更、定期巡检   |

### 6.3 冲突仲裁

| 层级冲突      | 裁决规则                          |
| ------------- | --------------------------------- |
| Rule 之间     | 更严格者优先                      |
| Skill 之间    | 项目级覆盖通用级                  |
| Rule vs Skill | Rule 不可降级，Skill 可扩展       |
| 无法裁决      | 提交技术负责人评审，裁决写入 Rule |

## 7 效果度量

| 维度   | 指标           | 目标    | 度量方式                        |
| ------ | -------------- | ------- | ------------------------------- |
| 覆盖率 | `docs/` 完备率 | ≥ 80%   | 脚本扫描必需文件存在性          |
| 准确率 | AI 引用命中率  | ≥ 95%   | CR 抽检：Agent 引用与代码一致性 |
| 时效性 | 知识年龄       | ≤ 90 天 | Git log 计算文档最后更新时间    |
| 响应   | 漂移项关闭时长 | ≤ 48h   | 任务跟踪系统统计                |
| 合规   | AI 违规率      | ≤ 5%    | CR 统计：因知识库缺失导致的错误 |
| 效率   | 功能对话轮数   | ≤ 5 轮  | 交互统计：需求到交付的平均轮数  |
